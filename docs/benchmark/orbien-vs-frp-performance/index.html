Orbien vs frp 性能测试方案

本文给出一套可复现、可对比的性能测试方案，用于评估 Orbien 与开源 frp 在内网穿透场景下的吞吐、延迟、并发与资源开销。按本文执行后，应能得到可直接横向对比的量化结果。

仓库内已有简要 iperf3 / wrk 用法（见根目录 benchmark/性能测试.md），本文在其基础上补齐：对比公平性、完整拓扑、测试矩阵、弱网模拟、资源采集、结果模板与分析口径。

1. 测试目标​

目标说明
吞吐上限TCP / UDP / HTTP 在隧道上的最大带宽
延迟开销相对「直连无隧道」的额外 RTT / 建连延迟
并发能力高连接数、多流并发下的稳定性与吞吐衰减
资源开销Server / Client 的 CPU、内存、句柄、带宽占用
特性代价TLS、压缩、多路复用 / 独立连接、不同传输协议的开销差异
弱网表现有限带宽、延迟、丢包下的可用吞吐与稳定性

不在本次范围（可后续单独立项）： 功能正确性回归、安全渗透、P2P、控制台 UI、证书申请流程。

2. 公平对比原则（必读）​

两边必须在同一套约束下测试，否则结论无效。

  1. 同一机器拓扑：同一台公网 Server 机、同一台内网 Client 机、同一台压测机（或明确标注「本机环回」场景）。
  2. 同一版本基线：记录 Orbien 版本、frp 版本、JDK / OS / 内核参数。
  3. 同一代理语义：优先对比「TCP 端口映射」与「HTTP 反向代理」；UDP 单独成章。
  4. 关闭干扰特性：默认对照组关闭限速、关闭压缩、关闭额外加密（除协议自身 TLS）；需要测特性代价时再单变量打开。
  5. 先测直连基线：无隧道时的本机 / 跨机直连吞吐，作为天花板。
  6. 每组至少 3 次：取中位数；标注方差过大时的原因（CPU 抢占、温控降频、磁盘等）。
  7. 单变量原则：一次只改一个维度（如仅改 multiplex / 仅改 TLS）。
  8. 端口与防火墙：压测前确认端口已放行；两边监听端口可不同，但路径长度与网卡路径一致。
  9. 时间窗口一致：iperf3 默认 10s，正式对比建议统一 30s；HTTP 统一 30s。
  10. 排除热身偏差：每组正式跑前先 warm-up 一次，丢弃首次结果。

3. 推荐拓扑​

3.1 场景 A：本机环回（快速摸底）​

适合开发机快速对比上限与回归，不代表公网真实表现。

┌─────────────────────────────────────────────┐
│  同一台机器                                 │
│  iperf3/wrk Client ──► Server:remotePort    │
│         │                                   │
│         ▼                                   │
│  Orbien/frp Server ◄── Orbien/frp Client    │
│         │                    │              │
│         └──────────► localPort (iperf3 -s)  │
└─────────────────────────────────────────────┘

3.2 场景 B：双机内网（推荐主测）​

压测机 / 访客机                    公网或内网可达的 Server 机
┌──────────────┐                  ┌──────────────────────┐
│ iperf3 / wrk │── remotePort ──►│ Orbien/frp Server     │
└──────────────┘                  └──────────┬───────────┘
                                             │ 隧道
                                  ┌──────────▼───────────┐
                                  │ Orbien/frp Client    │
                                  │ + iperf3 -s / nginx  │
                                  └──────────────────────┘
                                         内网机

3.3 场景 C：跨公网（真实穿透）​

Client 在 NAT 后，Server 有公网 IP。用于验证真实延迟、丢包与 NAT 路径；带宽上限受运营商链路制约，需单独记录 ISP / 带宽套餐。

5. 被测软件部署​

以下给出最小可跑通的对照配置。正式测试请关闭带宽限制、健康检查抖动等非必要特性。

5.1 Orbien Server​

orbien-server.toml（性能测试精简版）：

server_addr = "0.0.0.0"
server_port = 9527
http_proxy_port = 8080
https_proxy_port = 8443

[[tokens]]
name = "bench"
token = "bench-token-change-me"

[transport.websocket]
enabled = true
server_port = 9528
path = "/tunnel"

[transport.quic]
enabled = true
server_port = 9529

[dashboard]
enabled = false

[[port_pool.tcp]]
start = 19050
end = 19099

[[port_pool.udp]]
start = 19050
end = 19099

启动示例：

# Docker
docker run --rm --network host \
  -v "$PWD/orbien-server.toml:/app/orbien-server.toml" \
  lxien/orbien-server:0.24.0

# 或本地 jar
java -Xms1g -Xmx1g -jar orbien-server.jar -c orbien-server.toml
JVM 建议

对比吞吐时固定堆大小（如 -Xms1g -Xmx1g），避免动态扩堆干扰；记录 GC 日志可选：-Xlog:gc*:file=gc-orbien.log。

5.2 Orbien Client​

orbien-bench.toml：

server_addr = "SERVER_IP"
server_port = 9527

[auth]
token = "bench-token-change-me"

[transport]
protocol = "tcp"

[transport.multiplex]
enabled = true

[[proxies]]
name = "bench-tcp"
protocol = "tcp"
local_ip = "127.0.0.1"
local_port = 5201
remote_port = 19051

[[proxies]]
name = "bench-udp"
protocol = "udp"
local_ip = "127.0.0.1"
local_port = 5202
remote_port = 19061

[[proxies]]
name = "bench-http"
protocol = "http"
local_ip = "127.0.0.1"
local_port = 18080
custom_domains = ["bench.local.test"]

启动：

orbien run orbien-bench.toml
# 或
docker run --rm --network host \
  -v "$PWD/orbien-bench.toml:/app/orbien.toml" \
  lxien/orbien:0.24.0

对照矩阵用代理级覆盖示例（单变量打开）：

# 关闭多路复用（独立直连）
[proxies.transport]
multiplex = false

# 开启压缩
[proxies.transport]
compress = true
compress_algorithm = "snappy"   # 或 lz4 / zstd

# 切换传输协议
[proxies.transport]
protocol = "websocket"          # 或 quic / tcp

5.3 frp Server​

frps.toml（frp v0.52+ TOML 风格；旧版用 ini 亦可，语义对齐即可）：

bindPort = 7000
vhostHTTPPort = 8081
# 如需 dashboard 可关，减少干扰
./frps -c frps.toml

5.4 frp Client​

frpc.toml：

serverAddr = "SERVER_IP"
serverPort = 7000

[[proxies]]
name = "bench-tcp"
type = "tcp"
localIP = "127.0.0.1"
localPort = 5201
remotePort = 19052

[[proxies]]
name = "bench-udp"
type = "udp"
localIP = "127.0.0.1"
localPort = 5202
remotePort = 19062

[[proxies]]
name = "bench-http"
type = "http"
localIP = "127.0.0.1"
localPort = 18080
customDomains = ["bench.local.test"]
./frpc -c frpc.toml
与 Orbien 的对等关系
能力Orbienfrp对比建议
TCP/UDP/HTTP 代理有有主对比
多路复用默认开，可关有 transport 相关能力，版本差异大各用默认 + 再测「关复用」
隧道 TLS可开可开单独对比「开启加密」组
压缩snappy/lz4/zstd有限 / 插件差异标注「仅 Orbien」或找对等配置
WebSocket / QUIC 传输有能力不对等单列特性测试，不强行对等

6. 后端目标服务​

6.1 TCP：iperf3​

在 Client 所在机器（被穿透侧）启动：

iperf3 -s -p 5201 -i 1

6.2 UDP：iperf3​

iperf3 -s -p 5202 -i 1

6.3 HTTP：静态或简单 API​

推荐用 nginx 提供固定大小文件，便于测吞吐：

# 生成测试文件
mkdir -p /tmp/bench-www
dd if=/dev/urandom of=/tmp/bench-www/1k.bin  bs=1024 count=1
dd if=/dev/urandom of=/tmp/bench-www/64k.bin bs=1024 count=64
dd if=/dev/urandom of=/tmp/bench-www/1m.bin  bs=1M   count=1

# nginx 监听 18080，root 指向 /tmp/bench-www
# 或用 python 快速起静态站（仅摸底，正式建议 nginx）：
python3 -m http.server 18080 --directory /tmp/bench-www

小对象（1KB）偏重并发与调度；大对象（1MB）偏重吞吐。

6.4 连通性自检​

# TCP
nc -vz SERVER_IP 19051

# HTTP（按域名 / Host）
curl -v -H "Host: bench.local.test" http://SERVER_IP:8080/1k.bin -o /dev/null

8. 详细测试步骤​

8.0 通用流程（每组用例）​

  1. 确认 Server、Client 已连接（控制台 / 日志无报错）。
  2. 确认目标服务（iperf3 / nginx）在跑。
  3. 启动资源采集（见第 9 节）。
  4. Warm-up 跑 1 次，丢弃结果。
  5. 正式跑 3 次，记录每次原始输出。
  6. 停止资源采集，归档日志。
  7. 换产品（Orbien ↔ frp）时不要同时跑两套，避免抢核与抢带宽。

建议结果目录结构：

bench-results/
  2026-07-29/
    env.md
    baseline/
    orbien/
      T1-tcp-forward-1.txt
      T1-tcp-forward-2.txt
      ...
      resources-T1.csv
    frp/
      ...
    summary.csv

8.1 B0 — 直连基线（无隧道）​

在同一对机器上，压测机直连内网机的 5201（需网络可达）：

# 内网机
iperf3 -s -p 5201

# 压测机
iperf3 -c INNER_IP -p 5201 -t 30 -i 1
iperf3 -c INNER_IP -p 5201 -t 30 -i 1 -R
iperf3 -c INNER_IP -p 5201 -t 30 -i 1 -P 4

本机环回场景则 INNER_IP=127.0.0.1。该结果是「物理链路 + OS 栈」上限。

8.2 T1 / T2 — TCP 单向 / 反向吞吐 ★​

Orbien：访客访问 SERVER_IP:19051 → 隧道 → 127.0.0.1:5201。

# 内网机（Client 侧）
iperf3 -s -p 5201

# 压测机（可与 Server 同机，也可独立）
# 正向：压测机 → Server remote → Client local（数据发向 server 侧）
iperf3 -c SERVER_IP -p 19051 -t 30 -i 1 | tee orbien/T1-tcp-forward-1.txt

# 反向：-R
iperf3 -c SERVER_IP -p 19051 -t 30 -i 1 -R | tee orbien/T2-tcp-reverse-1.txt

frp：端口改为 19052，命令相同。

记录指标：sender / receiver Bitrate（Gbits/sec 或 Mbits/sec）、是否出现重传异常（iperf3 详细模式）。

8.3 T3 — TCP 多并行流​

iperf3 -c SERVER_IP -p 19051 -t 30 -P 1
iperf3 -c SERVER_IP -p 19051 -t 30 -P 4
iperf3 -c SERVER_IP -p 19051 -t 30 -P 8
iperf3 -c SERVER_IP -p 19051 -t 30 -P 16

观察：总吞吐是否随并行度上升；Orbien 多路复用下连接数与 frp 的差异（配合 ss -s / lsof）。

8.4 H1 — HTTP 小文件高并发 ★​

确保 Host 能路由到对应 HTTP 代理（本地可改 /etc/hosts：SERVER_IP bench.local.test）。

# Orbien（http_proxy_port=8080）
wrk -t12 -c400 -d30s --latency \
  -H "Host: bench.local.test" \
  http://SERVER_IP:8080/1k.bin \
  | tee orbien/H1-http-1k-1.txt

# frp（vhostHTTPPort=8081）
wrk -t12 -c400 -d30s --latency \
  -H "Host: bench.local.test" \
  http://SERVER_IP:8081/1k.bin \
  | tee frp/H1-http-1k-1.txt

统一参数建议：

参数值说明
-tCPU 逻辑核数或 12两边相同
-c100 / 400 / 1000阶梯加压
-d30s正式对比

记录：Requests/sec、Transfer/sec、Latency avg/stdev/max、Latency Distribution（50/75/90/99）。

8.5 H2 — HTTP 大文件吞吐​

wrk -t4 -c32 -d30s --latency \
  -H "Host: bench.local.test" \
  http://SERVER_IP:8080/1m.bin

也可用多次 curl 测单连接吞吐：

curl -o /dev/null -w "time_total=%{time_total} size=%{size_download} speed=%{speed_download}\n" \
  -H "Host: bench.local.test" \
  http://SERVER_IP:8080/1m.bin

8.6 U1 — UDP​

# Client 侧
iperf3 -s -p 5202

# 压测机：-b 为目标带宽上限，从低到高扫，直到丢包率明显上升
iperf3 -c SERVER_IP -p 19061 -u -b 100M -t 30 -i 1
iperf3 -c SERVER_IP -p 19061 -u -b 500M -t 30 -i 1
iperf3 -c SERVER_IP -p 19061 -u -b 1G   -t 30 -i 1

记录：Bitrate、Jitter、Lost/Total datagrams。UDP 对缓冲与调度极敏感，务必双边相同 OS 与缓冲参数。

8.7 L1 — 延迟开销​

HTTP 建连 + TTFB（小响应）：

# 连续 100 次，统计
for i in $(seq 1 100); do
  curl -o /dev/null -s -w "%{time_connect} %{time_starttransfer} %{time_total}\n" \
    -H "Host: bench.local.test" \
    http://SERVER_IP:8080/1k.bin
done | awk '{c+=$1;s+=$2;t+=$3;n++} END{printf("avg connect=%.4f start=%.4f total=%.4f\n",c/n,s/n,t/n)}'

对比：直连后端 http://INNER_IP:18080/1k.bin 与经 Orbien / frp 的差值，即为隧道附加延迟（近似）。

8.8 C1 — 短连接冲击​

# hey：总请求数与并发
hey -n 20000 -c 200 -host bench.local.test http://SERVER_IP:8080/1k.bin

观察错误率、超时、Server/Client CPU、是否出现连接耗尽。

8.9 S1 — 长稳（Soak）​

# 例：1 小时低并发持续
wrk -t2 -c50 -d1h --latency \
  -H "Host: bench.local.test" \
  http://SERVER_IP:8080/1k.bin

期间每 5 分钟采样一次 RSS / 句柄数：

# Linux 示例，ORB_PID 为进程 PID
while true; do
  date +%s
  ps -p "$ORB_PID" -o pid,pcpu,pmem,rss,vsz
  ls /proc/$ORB_PID/fd 2>/dev/null | wc -l
  sleep 300
done | tee soak-orbien.txt

8.10 W1 — 弱网（Linux tc netem）​

在 Server 机出口 或中间网卡加规则（示例对 eth0）：

# 加：50ms 延迟 + 1% 丢包
sudo tc qdisc add dev eth0 root netem delay 50ms loss 1%

# 限速示例（配合 HTB，按环境调整）
# sudo tc qdisc add dev eth0 root tbf rate 100mbit burst 32kbit latency 400ms

# 清除
sudo tc qdisc del dev eth0 root

在弱网下重复 T1、H1，对比 Orbien（尤其 QUIC）与 frp 的吞吐与错误率。

8.11 F1–F4 — Orbien 特性单变量​

每次只改 Client 一处配置，其余保持与 T1/H1 相同：

组变更预期观察
F1multiplex=true/false高并发下连接数、吞吐、CPU
F2隧道 TLS on/off吞吐下降比例、CPU 上升
F3compress on/off + 算法可压缩文本（如重复 JSON）才有意义；随机二进制可能更慢
F4protocol=tcp/websocket/quic吞吐、延迟、弱网表现

压缩组建议后端改为 gzip 前的高冗余文本文件，而不是 /dev/urandom。

9. 资源与系统监控​

压测同时采集，否则无法解释「谁更快但更吃 CPU」。

9.1 进程级（推荐）​

# 找到 PID
pgrep -af orbien
pgrep -af frps
pgrep -af frpc

# Linux：每秒采样
pidstat -p <PID> 1 | tee resources-cpu.txt
pidstat -r -p <PID> 1 | tee resources-mem.txt

# macOS
# top -pid <PID> -l 0 -s 1

9.2 连接与句柄​

# Linux
ss -s

11. 分析口径与结论写法​

  1. 吞吐：优先看 iperf3 receiver 侧；HTTP 看 Transfer/sec 与 RPS，并注明对象大小。
  2. 效率：定义 效率 = 隧道吞吐 / 直连吞吐，比绝对 Gbps 更利于跨机器对比。
  3. 延迟：报告 P50 / P99，避免只报平均值。
  4. 资源：在相近吞吐下比较 CPU；或在相同 CPU 预算下比较吞吐。
  5. 稳定性：3 次结果相对标准差 > 10% 时，排查温控、同机干扰、GC、后台任务后重测。
  6. 不对等能力：QUIC / 压缩算法等写在「Orbien 特性」章节，不要塞进「对等对比总分」。
  7. 禁止：在未关限速、未统一时长、两边同时压测抢带宽时发布对比结论。

13. 常见问题与排障​

现象可能原因处理
吞吐极低限速、Wi-Fi、节能、Docker 桥接关限速；有线；--network host
Orbien 远低于预期TLS+压缩同时开、堆过小频繁 GC单变量关闭；加大堆并看 GC
frp / Orbien 差一个数量级测到了环回 vs 跨机混用统一拓扑
HTTP 404 / 502Host / 域名未匹配检查 customDomains 与 Host 头
UDP 丢包爆表-b 设太高或缓冲不足阶梯降带宽；调 net.core.rmem_*
结果抖动大同机浏览器/索引、CPU 睿频关无关进程；绑核；多次取中位数
端口冲突19051 等被占用lsof -i :19051
